# Decisions

Architectural and technical decisions made in this project.
Each entry documents WHAT was decided and WHY.

## 2026-04-27: Custom Session System Over NextAuth Sessions
- **Choice**: API routes use a hand-rolled cookie-based session system (`session-token` cookie → `Session` table) instead of NextAuth's `getServerSession()`
- **Reason**: Simpler cookie-based auth that integrates directly with the Prisma `Session` model and enables admin role checks
- **Considered**: Using NextAuth JWT sessions exclusively via the configured `[...nextauth]` route
- **Tradeoff**: NextAuth v4 is configured but unused by the UI; dual auth code exists but only the custom system is active

## 2026-04-27: Prisma Client Inside App Directory
- **Choice**: Prisma generator outputs to `../app/generated/prisma` instead of the default `node_modules/.prisma/client`
- **Reason**: Bundles the generated client with the app code, avoids node_modules resolution quirks in Next.js
- **Considered**: Default output path
- **Tradeoff**: Must run the client regeneration after schema changes; import path is relative (`"../app/generated/prisma"`) not via `@prisma/client`. Since #151 the regeneration runs automatically on `npm install` (`postinstall`) and is wrapped as `npm run prisma:generate`

## 2026-04-27: PostgreSQL Over SQLite
- **Choice**: Migrated database from SQLite to PostgreSQL 16
- **Reason**: Needed for production deployment; SQLite was a dev-only stopgap (issue #45)
- **Considered**: Staying on SQLite
- **Tradeoff**: Requires Docker/PostgreSQL running locally; adds infrastructure complexity

## 2026-04-27: Service Layer Pattern
- **Choice**: All business logic moved from API route handlers into dedicated `services/*.ts` modules
- **Reason**: Separates HTTP concerns from business logic, improves testability and reuse
- **Considered**: Logic inline in route handlers (was the prior pattern)
- **Tradeoff**: More files; must follow the pattern consistently

## 2026-04-27: MinIO for File Storage
> Superseded 2026-10-17 by "PostgreSQL blobs instead of MinIO" (#131).
- **Choice**: Files stored in MinIO (S3-compatible container) instead of local filesystem or database
- **Reason**: Production-ready object storage that avoids filesystem coupling; enables scaling (issue #58)
- **Considered**: Local filesystem storage, PostgreSQL BYTEA columns
- **Tradeoff**: Requires MinIO container running; adds a second infrastructure dependency alongside PostgreSQL

## 2026-04-27: English as UI Language
- **Choice**: Switched all UI text from German to English (commit #57)
- **Reason**: Consistent with codebase (code comments are English), broader accessibility
- **Considered**: Keeping German, or supporting both
- **Tradeoff**: Legacy German strings may still exist in older components

## 2026-09-22: Pin @types/node via npm overrides
- **Choice**: Force `@types/node` to the root `^20` spec for all nested dependents via `"overrides": { "@types/node": "$@types/node" }` in `package.json` (issue #112)
- **Reason**: `vitest@5.0.1` declares peerOptional `@types/node@"^22.0.0 || >=24.0.0"`, so `npm ci` on clean machines (CI) pulled `@types/node@26` and died with ERESOLVE before lint/tests ran; overrides keep a single v20 tree deterministically
- **Considered**: Bumping `@types/node` to ^22/^24 (larger blast radius), downgrading vitest (wrong direction), `--legacy-peer-deps` in workflow/hook (masks instead of fixing)
- **Tradeoff**: If a future dependency genuinely needs `@types/node ≥ 22` types, the override must be revisited

## 2026-09-22: Add typecheck gate; stop suppressing pre-push gate output
- **Choice**: Add `"typecheck": "tsc --noEmit"` to `package.json` and run it in both `.github/workflows/test.yml` and `.githooks/pre-push`, alongside lint and tests (issue #112). Also removed the `>/dev/null 2>&1` redirects in the pre-push hook so a gate failure prints its real output inline instead of pointing to a second manual run.
- **Reason**: `AGENTS.md` previously noted "no typecheck script is configured" — TypeScript errors only surfaced at `next build`, so the lint+test gate could still let a broken build through. Suppressed hook output also meant every local failure required re-running the command by hand to see why.
- **Considered**: Leaving typecheck to `next build` only (status quo) — rejected because it means the pre-push/CI gate isn't actually a complete correctness gate.
- **Tradeoff**: `tsc --noEmit` adds a few seconds to both the pre-push hook and CI run.

## 2026-09-28: Mock I/O modules in unit tests instead of pure-logic-only
- **Choice**: Unit tests may replace `@/lib/prisma`, `@/lib/minio`, `@/lib/mailer`, `bcrypt`, `nodemailer`, `minio` and `fetch` with `vi.mock` / `vi.stubGlobal`. Inner helpers are lifted to module level and exported for tests (marked `// Exported for unit tests (#112).`), without behaviour changes (issue #112).
- **Reason**: The "pure logic only" rule left the most important logic untested — role/permission checks in `adminService.updateUser`/`deleteUser`, session expiry, the Excel import into the DB. Mocks keep `npm test` fast and infrastructure-free, so it still runs in the pre-push hook and CI.
- **Considered**: Pure logic only (status quo, leaves permissions untested); integration tests against a Docker PostgreSQL/MinIO (slow, needs services in CI and the hook).
- **Tradeoff**: Mocks encode the current Prisma call shapes — renaming a query argument breaks tests even if behaviour is unchanged. Real DB constraints are not exercised.

## 2026-04-27: Enum-based State Management
- **Choice**: Upload and password reset states use Prisma enums (`UploadStates`, `PasswordResetStates`) instead of raw strings
- **Reason**: Type safety and self-documenting state transitions
- **Considered**: String-based states
- **Tradeoff**: Enum values are hard-coded in schema; changing them requires migration

## 2026-10-16: No self-managed maintenance tunnels into the BOKUnet
- **Choice**: Maintenance access to the BOKU production server goes only through the paths the university sanctions — BOKU VPN (Cisco AnyConnect) with the Funktionsaccount + MFA (#84), or on-site (#122). No server-initiated standing tunnel: neither an external VPN bridging the server into a third-party network, nor a reverse SSH tunnel to a VPS, nor that same tunnel carried inside HTTPS/WebSocket (a `wstunnel`-style reverse tunnel, i.e. `ssh` through an existing nginx TLS vhost). From the network's point of view all three are the same thing.
- **Reason**: A permanent outbound connection creates inbound reachability into the department segment — an approval-required active network component and a firewall bypass — regardless of whether a `tun0` interface appears and regardless of whether the carrier is TCP/22 or TLS/443. BOKUnet rules forbid split tunnelling, require prior written approval for active network components, and BOKU-IT can take an entire subnet off the network on violation. Full sourced reasoning in #115.
- **Considered**: (a) server joins a self-operated external VPN — rejected; (b) permanent reverse SSH tunnel (server → VPS, `ssh localhost:2222` at the VPS) — rejected; (c) the same reverse tunnel wrapped in HTTPS/WebSocket (TLS carrier with WebSocket multiplexing, e.g. `wstunnel -R`, or plain `ssh` behind a dedicated nginx TLS vhost) — rejected: functionally identical to (b), only the encapsulation differs. It is *more* tempting than (b) precisely because it survives a firewall that blocks port 22 — which is exactly the property that makes it a bypass rather than a sanctioned path. The surrounding technique remains legitimate for infrastructure Georg owns (e.g. reaching claw or his own devices), where he is the network owner; it is excluded here only because of who owns the BOKUnet. (d) hosting the app externally on Georg's own VPS, which removes the need for BOKUnet maintenance access altogether — open, needs the client's consent (data protection / responsibility). (e) on-site maintenance only until BOKU-IT answers — the current fallback.
- **Tradeoff**: Until BOKU-IT answers (#115) or an on-site visit happens (#122) there is no direct maintenance path at all — no "fix it quickly" option, and every intervention needs a coordinated appointment. Accepted deliberately: the downside of a firewall bypass (subnet removal, loss of VPN/account rights) is far larger than the downside of slow maintenance.

## 2026-10-17: Dev-Instanz selbstgebautes MinIO, mc aus apt
> Obsolet seit 2026-10-17: MinIO wird durch PostgreSQL-Blobs ersetzt (#131); die `minio.service`-Unit und `mc` werden nicht mehr gebraucht.
- **Choice**: On the `catchlogx.graf.priv.at` dev instance, MinIO runs as a binary built from the upstream source tarball of tag `RELEASE.2025-10-15T17-29-55Z` (`go build`, user unit `minio.service`); `mc` comes from Ubuntu's `minio-client` package instead of being built from source
- **Reason**: MinIO is no longer obtainable as a container image or prebuilt binary (repo archived 2026-04, Docker Hub blocked for the namespaces, `dl.min.io` answers 410, GitHub releases carry no assets, snap channels are 2018-era stubs); the upstream README now recommends building from source. `minio-client` is packaged and security-maintained in Ubuntu 26.04 universe, so building `mc` too would have been unnecessary work
- **Considered**: Docker image transfer from another host, S3 alternatives (Garage/SeaweedFS), snap (`minio` snap only has an unmaintained 2018 edge build)
- **Tradeoff**: MinIO server binary is not updated by apt and must be rebuilt manually from a newer tag; build needs a Go toolchain (`golang-go` from apt) and ~2 min link step on this VPS

## 2026-10-17: Befischungsdaten in eigenem privaten Repo, nicht hier
- **Choice**: Die Excel-Datenlieferungen der BOKU-Hydrobiologie liegen im privaten Schwesterrepo `georgernstgraf/CatchLogX-Data` (Trunk `main`, kein Git LFS, Struktur 1:1 wie geliefert). Dieses Repo enthält ausschließlich Anwendungscode.
- **Reason**: CatchLogX ist **public** — Forschungsdaten dürfen dort nicht hinein. Ein eigenes Repo hält die Code-Historie klein und lässt den Bestand generationenweise (Roh-Export / Lenas Überarbeitung / Letztstand) versionieren (#125).
- **Considered**: (a) Daten in CatchLogX committen — abgelehnt, public; (b) Git LFS im Datenrepo — abgelehnt, 1 GB Storage/Monat Gratis-Quota und `git lfs install`-Zwang für jeden Klon; (c) eigener Branch im selben Repo — abgelehnt, Historie und Zugriffsrechte nicht trennbar.
- **Tradeoff**: Ohne LFS kostet jede künftige Datenlieferung die volle Dateigröße in der Git-Historie. Zugriffsrechte müssen in zwei Repos gepflegt werden.

## 2026-10-17: Migration-only-Schema-Workflow, Baseline-Neubau statt resolve (#129)
> Superseded 2026-10-18 by "Datenerhaltende Übernahme der Produktionsdatenbank" (#145) — betrifft nur den geplanten Prod-Neuaufbau, nicht den Migrations-Workflow selbst.
- **Choice**: Die Migrations-History ist ab jetzt die **einzige** Schema-Wahrheit: eine einzige, aus `schema.prisma` generierte Baseline (`20261017190000_init`); Schema-Änderungen laufen über `prisma migrate dev`, Deploy über `prisma migrate deploy`; `prisma db push` ist verbannt. Die Dev-DB wurde aus der Baseline neu aufgebaut; die BOKU-Produktion wird **nicht** neu aufgebaut, sondern beim Wartungstermin (#122) datenerhaltend adoptiert (siehe 2026-10-18).
- **Reason**: Die bisherige History log (`User.role` als `TEXT DEFAULT 'viewer'` statt des Enum `UserRoles`), weil seit April jede Schema-Änderung per `db push` an ihr vorbeilief — ein `migrate deploy` auf leerer DB hätte ein falsches Schema erzeugt. `db push` schreibt keine Migration, versioniert nichts und droppt bei Umbenennungen Tabellen (Datenverlust, siehe #128, wo nur ein manuelles `ALTER TABLE` half).
- **Considered**: (a) `migrate resolve --applied`-Baselining der existierenden History — verworfen, weil die Dev-Datenbank ohnehin nur Seed-Daten enthält und ein Neuaufbau die History gleich beweist; (b) History reparieren durch Nachtragen der fehlenden Enum-Migration — verworfen zugunsten der sauberen Einzel-Baseline; (c) weiter `db push` — verworfen.
- **Tradeoff**: Ein CI-Drift-Gate (`.github/workflows/test.yml`, Job `migration-drift`) hält die Regel künftig mechanisch durchsetzbar; Entwickler brauchen zusätzlich einen Shadow-DB-Eintrag (`SHADOW_DATABASE_URL`) für `migrate dev`.

## 2026-10-17: PostgreSQL-Blobs statt MinIO (#131)
> Superseded 2026-10-18 by "Datenerhaltende Übernahme der Produktionsdatenbank" (#145) — betrifft nur den geplanten Prod-Neuaufbau und die Aussage, dass die Produktions-MinIO-Objekte nicht migriert werden.
- **Choice**: Dateiinhalte von User-Uploads und Vorlagen liegen als `bytea` in der eigenen Tabelle `FileBlob`; `Uploads` und `TemplateFiles` referenzieren sie über `blobId`. MinIO wird komplett entfernt (Code, Compose, `package.json`, dev-`minio.service`, Tests, Doku).
- **Reason**: MinIO war ein zweites Infrastruktur-System ohne gemeinsame Transaktion mit der DB (kein 2PC zwischen S3 und PostgreSQL). Für den Bulk-Import (#88) muss ein Upload **all-or-nothing** sein — mit Blobs in der DB wird das zu genau einer Transaktion. Zusätzlich: `pg_dump` sichert die Dateien mit (#86), ein bewegliches Teil weniger auf der Dev-Instanz, und die blosse Excel-Größenordnung macht die Bytes-in-DB-Frage trivial.
- **Considered**: (a) MinIO behalten + kompensierendes Löschen für Atomarität — verworfen, zwei Systeme bleiben konsistenzanfällig; (b) PostgreSQL Large Objects (`lo_*`, Streaming bis 4 TB) — verworfen, kein Prisma-Support, Raw-SQL nötig; (c) Blob-Spalte direkt auf `Uploads`/`TemplateFiles` — verworfen, Listen-Queries würden versehentlich Bytes laden; (d) Blobs im Dateisystem — verworfen, Backup/Deploy-Kopplung.
- **Tradeoff**: Prisma lädt `Bytes`-Werte vollständig in den Speicher (bei Excel-Dateien unkritisch, hart begrenzt bei ~1 GB/Wert); DB- und Backup-Größe (WAL) wachsen mit den Dateien. Die Dev-DB enthielt nur Seed-Vorlagen (per `npm run seed:demo` neu als Blob angelegt), dort werden keine MinIO-Objekte migriert; in der Produktion werden die 19 MinIO-Objekte (56.337.761 Bytes) bei der Adoption als `FileBlob`-Rows übernommen (#139), die Produktion wird **nicht** frisch aus der Baseline aufgebaut (siehe 2026-10-18).

## 2026-10-17: SHA-gekeyte Standalone-Releases statt Build-im-Restart (#135, #123)
- **Choice**: Die Dev-Instanz deployt **push-getrieben** aus der CI. Ein `deploy`-Job in `.github/workflows/test.yml` (nach `test` + `migration-drift`; `runs-on: [self-hosted, vps]`; nur bei Push auf `dev` oder manuellem Dispatch) baut mit `output: "standalone"`, veröffentlicht `~/releases/<sha>/` via `scripts/publish-release.sh` (setzt den Symlink `~/current` atomar um), führt `prisma migrate deploy` aus, startet `catchlogx.service` neu und prüft per HTTP-Health-Check. Der Service selbst führt nur `node ~/current/server.js` aus — ein Restart ist ein ~2 s Neustart **ohne** Build. `catchlogx-update.service` und `~/.config/catchlogx/deploy.sh` sind stillgelegt.
- **Reason**: Der alte Weg (jeder Restart = Pull → Tests → Build → Start) hatte zwei Fehler: (1) die Skip-Logik verglich HEAD vor/nach dem Pull und lieferte deshalb einen **veralteten Build** aus, wenn der Commit lokal schon existierte — der Nutzer sah keine Erfolgsmeldung nach dem Upload, weil die App noch den alten Stand servierte (#133); (2) ein `restart` war nie „nur ein Neustart". Mit einem Artefakt pro Commit ist „ist der Build aktuell?" nicht mehr falsch beantwortbar — **das Artefakt ist der SHA** — und Rollback wird ein Symlink-Wechsel.
- **Considered**: (a) Artefakt per SSH von GitHub-hosted Runnern übertragen — verworfen, GitHub soll sich nicht auf der VPS anmelden (keine Deploy-Keys in GitHub); (b) Änderungserkennung per mtime/`find -newer` wie `make` — verworfen als stiller Fehlermodus (Deletes, `.env`, `prisma generate`, `npm ci`-mtimes) und weil `next build` keinen deklarierten Dependency-Graph hat; (c) separater Workflow via `workflow_run` — verworfen, `workflow_run` lädt nur vom Default-Branch (`master`); (d) Runner als root-Service (GitHubs `svc.sh`) — verworfen, er könnte den User-Manager von `catchlogx` nicht erreichen.
- **Tradeoff**: Der Build läuft im Runner auf derselben 3,8-GB-VPS parallel zum laufenden Server (RAM-Druck wie zuvor, siehe #132); der `deploy`-Job liegt im Workflow `Test`, dessen `cancel-in-progress` einen laufenden Deploy abbrechen kann (selbstheilend: Symlink-Swap liegt vor dem Restart). Der Health-Check schlägt hart fehl, **kein** Auto-Rollback. Neue Abhängigkeit: `catchlogx-vps` muss laufen, sonst hängt der Deploy in der Queue.

## 2026-10-18: Datenerhaltende Übernahme der Produktionsdatenbank (#139, #141)
- **Choice**: Die BOKU-Produktionsdatenbank wird **nicht** aus der Baseline `20261017190000_init` neu aufgebaut, sondern in-place adoptiert: `scripts/adopt-legacy-prod.ts` (#139) benennt `DummyFiles` → `TemplateFiles` um, legt die Tabelle `FileBlob` an, befüllt pro referenziertem MinIO-Objekt einen Blob aus einem `mc mirror`-Export, setzt `Uploads.blobId`/`TemplateFiles.blobId` auf `NOT NULL`, droppt die MinIO-Pfadspalten (`DummyFiles.filePath`, `Uploads.link`), räumt die veraltete Migrations-Buchhaltung auf und markiert `20261017190000_init` und `20261017200000_replace_minio_with_file_blobs` als applied. Das Skript ist idempotent und per `--dry-run` probelauffähig. Der Cutover-Job (#141, `production-maintenance.yml`, `confirm=ADOPT-PRODUCTION`) verifiziert danach Drift, `migrate status`, Zeilenzahlen und Blobs, bevor er den neuen Stack hochfährt.
- **Reason**: Die Produktion enthält echte Nutzungsdaten (Fänge, Sessions, Password-Resets, Upload-Metadaten und 19 MinIO-Objekte). Ein Neuaufbau hätte die Rows verloren und die Objekte unverlinkt gelassen. Die Generalprobe (#140) hat den Pfad gegen eine echte Kopie der Produktionsdatenbank bewiesen (Run 39079039305: 19 Blobs / 56.337.761 Bytes, 464.654 Fänge, 18 Uploads, 1 Template, 7 User, 13 Sessions — alle Zeilenzahlen vor/nach identisch, Drift leer).
- **Considered**: (a) Produktion aus der Baseline neu aufbauen (der früher akzeptierte Plan, siehe 2026-10-17) — verworfen, Datenverlust; (b) `db push` beibehalten und auf den Baseline-Abgleich verzichten — verworfen, weil `db push` die History weiter umgeht und der Deploy-Pfad `migrate deploy` voraussetzt (siehe #129); (c) das Adoptionswerkzeug ohne Generalprobe direkt in Produktion laufen lassen — verworfen zugunsten der Rehearsal gegen eine Prod-Kopie (#140, Run 39079039305).
- **Tradeoff**: Die Adoption ist ein einmaliger, maschinenspezifischer Eingriff und wird im vereinbarten Vor-Ort-Fenster (#122) dispatcht, weil der Cutover die laufende App bewusst stoppt und die Produktion kurz offline nimmt; ein Rollback verlangt das verifizierte Pre-Cutover-Dump (`pg_restore`, #141). Die **Dev-DB wurde weiterhin aus der Baseline neu aufgebaut** (nur Seed-Daten) — der Produktions-Adoptionspfad lässt sich dort nicht üben.

## 2026-10-18: Immutable-Release-Topologie auch auf der Produktion (#143)
- **Choice**: Die Produktion betreibt die App nicht mehr als Container, sondern in derselben Form wie die Dev-Instanz: die App ist eine **systemd-User-Unit** `catchlogx.service` (`node ~/current/server.js`, `~/current` → `~/releases/<sha>/`), Node liegt als gepinntes offizielles Tarball unter `~/tools/node-v22.23.3` (`~/tools/node`-Symlink, glibc), die Laufzeitumgebung in `/opt/CatchLogX/.env` (mode 600, gitignored, übersteht `git reset --hard`). Ein Deploy baut **einmal im Job** mit nativem glibc-Node (`actions/setup-node` 22 — bewusst dieselbe Major wie die Laufzeit), ruft `scripts/publish-release.sh <sha>` (atomarer Symlink-Swap) und `systemctl --user restart`; ein Rollback ist ein erneutes Deploy des vorherigen `master`-Commits (der alte Release bleibt zusätzlich auf der Platte). Zwei neue Jobs in `production-maintenance.yml`: `machine-report` (read-only Bestandsaufnahme der Maschine) und `release-topology` (schreibt Node + Env-Datei + Unit) — letzterer mit denselben drei Gates wie `cutover` (dispatch-only, `master`-ref-guarded, `confirm=ADOPT-PRODUCTION`). Der Interim-Container `clx-web` wird beim ersten Release-Deploy retired; `docker-compose.prod.yml` legt den `app`-Service hinter das nie aktivierte Compose-Profil `interim-container`, damit ein versehentliches `docker compose up -d` die App nicht zurückholt.
- **Reason**: Der Interim-Deploy (#142) baute noch im Container und ließ die App mit kurzer Downtime als `next start`-Container (`clx-web`) neben der Container-DB dienen; das war ausdrücklich Zwischenlösung bis #143. Die Immutable-Release-Form macht einen Prod-Neustart zu einem ~2-s-Restart **ohne** Build (dieselbe Eigenschaft, die auf der Dev-Instanz seit #135 funktioniert), macht Rollback zu einem Commit-Dispatch statt zu einem Rebuild und entfernt die Docker-Abhängigkeit für die App (nur die Datenbank bleibt Container). `machine-report` trennt „erst messen" von „dann schreiben", damit die Unit-Provisionierung nicht auf unbekannter Maschinenlage raten muss.
- **Considered**: (a) App weiter im Container (wie #142) — verworfen, weil #143 genau die Dev-Topologie verlangt und ein Container-Restart-/Build-Pfad die Komplexität zurückbringt; (b) Node per Paket-Manager (apt) — verworfen, braucht sudo (Instituts-IT) und pinnt nicht auf genau die Dev-Major; (c) Alpine-Container-Build + Host-Runtime — verworfen: musl-Builds der nativen `bcrypt`/Prisma-Binaries laufen nicht auf glibc-Host-Node; (d) die `app`-Service per Default offen lassen und „kein `compose up`" nur dokumentieren — verworfen zugunsten des Profil-Guards (strukturell statt konventionell).
- **Tradeoff**: Die Maschine hält nun zwei Node-Installationen (Runner-Toolcache + `~/tools`); der Profil-Guard macht `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` auf Prod zur **DB-only**-Operation (die App startet nur mit `--profile interim-container`, was nichts tut). Linger muss für den Runner-User aktiv sein (`sudo loginctl enable-linger clxadmin`), sonst überlebt die Unit keinen Logout/Reboot — der Job meldet das als Warnung. `docker-compose.yml` (Basis) behält den `app`-Service weiterhin für die lokale Entwicklung; dass er auf Prod nicht startet, verhindert nur der Override.

## 2026-10-18: Read-only-DB-Rolle + bewusst offener Postgres-Port (#152)
- **Choice**: Port 5432 bleibt auf allen Interfaces offen (Docker publiziert `0.0.0.0:5432` — das war schon so); der Schutz ist die Rolle **`clx_readonly`** (SELECT auf alle Tabellen in `public`, **außer** `"User"`, `"Session"`, `"PasswordResets"`; `NOSUPERUSER`/`NOCREATEDB`/`NOCREATEROLE`, `CONNECTION LIMIT 20`, Default-Privileges für künftige Tabellen). Ein neuer, dreifach gegateter Dispatch-Job **`readonly-role`** in `production-maintenance.yml` legt sie an bzw. rotiert sie: das 12-Zeichen-Passwort wird **auf der Maschine** erzeugt (`openssl rand -base64 9`), **nie** gedruckt und **nie** als Repo-Secret gehalten; es wird zusätzlich als `READONLY_DB_PASSWORD` in `/opt/CatchLogX/.env` geschrieben (für die geplante In-App-Seite, #153). Re-Dispatch = Rotation.
- **Reason**: Wissenschaftliche Mitarbeiter brauchen Statistik-Zugriff per **R** (direkte `DBI`/`RPostgres`-Verbindung, Bulk-Analysen), den die App-Query-UI nicht leisten kann. Die Role ist genau der „echte Schutz", den die `validateSQLQuery`-Keyword-Blocklist laut `PITFALLS.md` nicht bietet. Die Auth-Tabellen sind ausgenommen, weil insbesondere `Session`-Tokens einer Kontoübernahme gleichkommen.
- **Considered**: (a) Port auf localhost beschränken (früherer #122-Punkt 7) — verworfen, der direkte Zugriff ist gewünscht; (b) Zugriff nur über die App-Query-UI — verworfen (kein R, keine Bulk-Workflows); (c) Einzel-Accounts pro Person — verworfen als Overhead, das geteilte Passwort out-of-band ist akzeptiert; (d) Passwort als Repo-Secret wie beim Smoke-Account — verworfen, weil es in die `.env` gehört (Anzeige) und an Menschen geht; (e) Passwort zeigt die geplante In-App-Seite **allen** eingeloggten Nutzern — akzeptiert, die Nutzerbasis ist geschlossen.
- **Tradeoff**: Das geteilte Passwort liegt im Klartext in `/opt/CatchLogX/.env` (mode 600) und wird an die Forschungsgruppe weitergegeben — kein Per-Person-Auditing. Statistik-Queries teilen sich die PostgreSQL-Instanz mit der App (Desktop-Klasse, 14 GiB RAM); `CONNECTION LIMIT 20` ist die Drossel. **`clxadmin` trägt weiterhin das Dev-Default-Passwort am selben offenen Port** — die Rotation ist damit dringlich, muss aber **nach** dem Unit-Cutover (#143) passieren, weil der laufende `clx-web`-Container das Passwort in seiner Compose-Umgebung gebacken hat.
