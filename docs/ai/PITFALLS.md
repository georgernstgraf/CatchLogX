# Pitfalls

Things that do not work, subtle bugs, and non-obvious constraints.
Read this file carefully before making changes in affected areas.

- Prisma client is at `app/generated/prisma/` — import as `"../app/generated/prisma"`, NOT `@prisma/client`. The generated directory is gitignored.
- After ANY schema change, run `npx prisma generate` — Next.js does not auto-regenerate the Prisma client
- Schema changes go through the migration history: `npx prisma migrate dev --name <name>` locally, `npx prisma migrate deploy` on the dev instance/production. **Never `prisma db push`** — it bypasses the history and drops/recreates tables on renames (that is how the history drifted before #129). Needs `SHADOW_DATABASE_URL` (`clx_shadow`) for local `migrate dev`
- `middleware.ts` runs in Edge Runtime — Prisma cannot be imported there. Keep it to lightweight cookie checks only
- Uploads are limited to **20 files / 500 MiB total / 32 MiB per file** (`MAX_UPLOAD_FILES`/`MAX_UPLOAD_TOTAL_BYTES`/`MAX_UPLOAD_FILE_BYTES` in `lib/uploadReport.ts`). There is **no row limit**: a "10,000 rows per file" rule lived only as UI text until it was briefly enforced, and it blocked the real BOKU bulk (14 files, 247,240 rows, 38 MB — `CatchLogX-Data`). **Two reverse-proxy settings must both be raised, or large uploads fail before the app sees them** (#132): `client_max_body_size` (nginx default 1m → **413**) *and* `proxy_read_timeout`/`proxy_send_timeout` (default 60s → **504** on a slow workbook). Both reach the browser as a generic error; `uploadFiles` now reports the HTTP status instead (`describeHttpFailure` in `lib/upload-client.ts`). Dev instance vhost: `client_max_body_size 550m`, timeouts `600s`.
- Bulk-upload memory/CPU is the real constraint for big workbooks, not the proxy: the route buffers the **whole body in memory** (`req.formData()`) and validation parses each workbook with SheetJS. Two measures keep it workable (#132): `XLSX.read(..., { dense: true })` (rows as arrays — measured ~2x faster and ~35% lower parse peak than the default sparse mode) and releasing each file's rows right after validation in `processBulkUpload` (re-read via `readDataRowsForAnnotation` only to annotate a failed workbook). Measured on the real 247k-row bulk: **~33 s** success path, **~77 s** when an error report is built, peak **~1.5 GB RSS** on this 3.8 GB VPS — i.e. close to the available memory. A 504'd request **keeps running server-side** and can still commit, so check `journalctl --user -u catchlogx.service` if a user reports a failure after a long upload.
- PostgreSQL must be running for any app to work (`docker compose up -d db`). File uploads and downloads need no extra service — bytes live in the DB (`FileBlob`, #131)
- `lib/mailer.ts` throws if nodemailer env vars are missing — password reset routes will fail without configured SMTP
- `scripts/create-user.ts` hardcodes `admin`/`admin` credentials — dev-only script, NOT for production
- Docker Compose `app` service runs `npx prisma migrate deploy` on every startup — it applies pending migrations only, never schema drift silently. The `db-shadow-init` service creates `clx_shadow` for `migrate dev` (#129)
- `no-explicit-any` ESLint rule is disabled — TypeScript `any` is allowed in this codebase
- `overrides` in `package.json` pins `@types/node` to the root spec (`"$@types/node"`): vitest 5 requires peerOptional `@types/node ^22 || >=24`, which breaks `npm ci` with ERESOLVE on clean machines while a stale local `node_modules` masks it. After touching any `@types/*` range, always verify with a fresh `rm -rf node_modules && npm install`.
- `next-env.d.ts` is gitignored and only auto-generated by `next dev`/`next build`. It carries `/// <reference types="next/image-types/global" />`, which is what makes `import x from "@/assets/img/foo.png"` typecheck. CI/the pre-push hook never run `next dev`/`next build`, so `npm run typecheck` (`tsc --noEmit`) fails there with `Cannot find module '...png'` even though it passes locally (where `next-env.d.ts` already exists from a prior dev run) — masked the same way the `@types/node` issue above was. Fixed by tracking `types/next-image.d.ts` with just that one reference line, independent of the gitignored file. To repro/verify locally: temporarily `mv next-env.d.ts next-env.d.ts.bak` before running `npm run typecheck`.
- `validateSQLQuery` (`services/queryService.ts`) is a keyword blocklist (whole-word match since #116), not a security boundary — it can't see through e.g. Postgres unicode-escaped identifiers. Real protection for the query UI would be a read-only DB role.
- Unit tests mock Prisma call shapes (`vi.mock("@/lib/prisma")`). Changing a query's `where`/`data`/`select` can fail tests that assert on those arguments even when behaviour is unchanged — adjust the assertion, don't delete the test.
- Self-hosted runners are selected by **label, not by branch**. Every self-hosted runner automatically carries `self-hosted`, `Linux` and `X64`, so two runners with only those automatic labels are *both* eligible for every `runs-on: [self-hosted, …]` job and placement becomes nondeterministic. The repo is a personal **user** account (`georgernstgraf`), so runner *groups* are not available as a scoping mechanism — custom labels are the only lever. Give each runner a distinct custom label (e.g. `boku-prod`, `vps-dev`) and never rely on the automatic ones alone. This matters concretely: `production-deploy.yml` does `cd /opt/CatchLogX`, which exists only on the BOKU machine. Since #136 each machine-specific job names its own custom label (`vps` → this VPS, `boku` → the BOKU machine), so placement is deterministic: `dev` builds on `vps`, `master` on `boku`. **Invariant**: only `master`-triggered workflows may name `boku` (the BOKU machine must never be pulled into `dev` work), and only the `dev` deploy job may name `vps`. A runner cannot filter by branch itself — the guard is discipline in the workflow files. Adding a new self-hosted job means giving it one of those labels (or a new one); never name only the automatic labels.
- Killing the npm wrapper process does **not** stop the Next server: `next start` runs as a separate child (`next-server`), and `kill <npm-pid>` (or even SIGTERM without `KillMode=mixed`) leaves the child holding port 40873 — the next start then loops on `EADDRINUSE`. Always manage the dev instance through systemd (`systemctl --user restart catchlogx.service`), never by killing raw PIDs. Since #135 the dev instance runs the standalone release directly (`node ~/current/server.js`, one process, no npm wrapper), but the warning still applies to anything started via `npm start`/`next start` (local dev, older setups).
- Two user units must never manage the same app/port. `clx-app.service` (the original 2026-10-17 dev-instance unit) raced with the new `catchlogx.service` for port 40873 and caused an `EADDRINUSE` restart loop; `clx-app.service` is now stopped + disabled. If a unit "respawns" an app you just killed, check `systemctl --user list-units | grep -i clx` first. (The oneshot `catchlogx-update.service` and `~/.config/catchlogx/deploy.sh` were retired in #135 — restarts no longer build.)
- Collaborator permissions cannot be set to read-only via the API on a **user-owned** repo. `PUT /repos/{owner}/{repo}/collaborators/{user}` accepts the `permission` parameter only for organization-owned repositories: anything other than `push` (i.e. `pull`/`read`/`triage`/`maintain`) fails with `422 Cannot assign {user} permission of {role}`. Such repos therefore always invite new collaborators with write access; read-only roles have to be assigned afterwards in the web UI (Settings → Collaborators and teams → Read). Hit while setting up `CatchLogX-Data` (#125).
- `output: "standalone"` (`next.config.ts`, #135) makes `next build` copy the **whole source tree** into `.next/standalone/` — including `*.test.ts`, `docs/`, and stray files like `Fischnamen.xlsx`. Two consequences: (a) anything that scans the repo for files must exclude `.next` — Vitest did **not** and ran 6 duplicated failing test files until `exclude: [..., ".next/**"]` was added to `vitest.config.ts`; (b) published release dirs carry that noise (`docs/` inside a release is expected).
- A **self-hosted runner on a public repo** (this repo is public) means any job a fork can trigger would execute on our hardware. Mitigation in place (#135): the `deploy` job is guarded `if: github.ref == 'refs/heads/dev' && (push || workflow_dispatch)`, so fork PRs never reach the VPS runner. Keep that guard on any new self-hosted job; keep PR jobs on GitHub-hosted runners.
