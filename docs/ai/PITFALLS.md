# Pitfalls

Things that do not work, subtle bugs, and non-obvious constraints.
Read this file carefully before making changes in affected areas.

- Prisma client is at `app/generated/prisma/` — import as `"../app/generated/prisma"`, NOT `@prisma/client`. The generated directory is gitignored and fully untracked, so nothing in git history or CI regenerates it.
- After ANY schema change, run `npm run prisma:generate` (#151) — Next.js does not auto-regenerate the Prisma client. `npm install` now also regenerates it via the `postinstall` script, but a bare `git pull` does not: pulling a schema refactor leaves the client stale until a regenerate or install. Symptom when stale: dozens of `Property 'X' does not exist on type 'PrismaClient'` / unknown-relation typecheck errors (37 errors after pulling the #131 blob refactor), which the pre-push hook turns into an aborted push even though the code itself is fine and CI is green. Fix is always `npm run prisma:generate`, never a code change.
- Schema changes go through the migration history: `npx prisma migrate dev --name <name>` locally, `npx prisma migrate deploy` on the dev instance/production. **Never `prisma db push`** — it bypasses the history and drops/recreates tables on renames (that is how the history drifted before #129). Needs `SHADOW_DATABASE_URL` (`clx_shadow`) for local `migrate dev`
- `middleware.ts` runs in Edge Runtime — Prisma cannot be imported there. Keep it to lightweight cookie checks only
- Uploads are limited to **20 files / 500 MiB total / 32 MiB per file** (`MAX_UPLOAD_FILES`/`MAX_UPLOAD_TOTAL_BYTES`/`MAX_UPLOAD_FILE_BYTES` in `lib/uploadReport.ts`). There is **no row limit**: a "10,000 rows per file" rule lived only as UI text until it was briefly enforced, and it blocked the real BOKU bulk (14 files, 247,240 rows, 38 MB — `CatchLogX-Data`). **Two reverse-proxy settings must both be raised, or large uploads fail before the app sees them** (#132): `client_max_body_size` (nginx default 1m → **413**) *and* `proxy_read_timeout`/`proxy_send_timeout` (default 60s → **504** on a slow workbook). Both reach the browser as a generic error; `uploadFiles` now reports the HTTP status instead (`describeHttpFailure` in `lib/upload-client.ts`). Dev instance vhost: `client_max_body_size 550m`, timeouts `600s`.
- Bulk-upload memory/CPU is the real constraint for big workbooks, not the proxy: the route buffers the **whole body in memory** (`req.formData()`) and validation parses each workbook with SheetJS. Two measures keep it workable (#132): `XLSX.read(..., { dense: true })` (rows as arrays — measured ~2x faster and ~35% lower parse peak than the default sparse mode) and releasing each file's rows right after validation in `processBulkUpload` (re-read via `readDataRowsForAnnotation` only to annotate a failed workbook). Measured on the real 247k-row bulk: **~33 s** success path, **~77 s** when an error report is built, peak **~1.5 GB RSS** on this 3.8 GB VPS — i.e. close to the available memory. A 504'd request **keeps running server-side** and can still commit, so check `journalctl --user -u catchlogx.service` if a user reports a failure after a long upload.
- PostgreSQL must be running for any app to work (`docker compose up -d db`). File uploads and downloads need no extra service — bytes live in the DB (`FileBlob`, #131)
- `lib/mailer.ts` throws if nodemailer env vars are missing — password reset routes will fail without configured SMTP
- `scripts/create-user.ts` hardcodes `admin`/`admin` credentials — dev-only script, NOT for production
- Docker Compose `app` service runs `npx prisma migrate deploy` on every startup — it applies pending migrations only, never schema drift silently. The `db-shadow-init` service creates `clx_shadow` for `migrate dev` (#129)
- `no-explicit-any` ESLint rule is disabled — TypeScript `any` is allowed in this codebase
- `overrides` in `package.json` pins `@types/node` to the root spec (`"$@types/node"`): vitest 5 requires peerOptional `@types/node ^22 || >=24`, which breaks `npm ci` with ERESOLVE on clean machines while a stale local `node_modules` masks it. After touching any `@types/*` range, always verify with a fresh `rm -rf node_modules && npm install`.
- `next-env.d.ts` is gitignored and only auto-generated by `next dev`/`next build`. It carries `/// <reference types="next/image-types/global" />`, which is what makes `import x from "@/assets/img/foo.png"` typecheck. CI/the pre-push hook never run `next dev`/`next build`, so `npm run typecheck` (`tsc --noEmit`) fails there with `Cannot find module '...png'` even though it passes locally (where `next-env.d.ts` already exists from a prior dev run) — masked the same way the `@types/node` issue above was. Fixed by tracking `types/next-image.d.ts` with just that one reference line, independent of the gitignored file. To repro/verify locally: temporarily `mv next-env.d.ts next-env.d.ts.bak` before running `npm run typecheck`.
- `validateSQLQuery` (`services/queryService.ts`) is a keyword blocklist (whole-word match since #116), not a security boundary — it can't see through e.g. Postgres unicode-escaped identifiers. Real protection for the query UI would be a read-only DB role.
- Unit tests mock Prisma call shapes (`vi.mock("@/lib/prisma")`). Changing a query's `where`/`data`/`select` can fail tests that assert on those arguments even when behaviour is unchanged — adjust the assertion, don't delete the test.
- Self-hosted runners are selected by **label, not by branch**. Every self-hosted runner automatically carries `self-hosted`, `Linux` and `X64`, so two runners with only those automatic labels are *both* eligible for every `runs-on: [self-hosted, …]` job and placement becomes nondeterministic. The repo is a personal **user** account (`georgernstgraf`), so runner *groups* are not available as a scoping mechanism — custom labels are the only lever. Give each runner a distinct custom label (e.g. `boku-prod`, `vps-dev`) and never rely on the automatic ones alone. This matters concretely: `production-deploy.yml` does `cd /opt/CatchLogX`, which exists only on the BOKU machine. Since #136 each machine-specific job names its own custom label (`vps` → this VPS, `boku` → the BOKU machine), so placement is deterministic: `dev` builds on `vps`, `master` on `boku`. **Invariant**: only `master`-triggered workflows may name `boku` (the BOKU machine must never be pulled into `dev` work), and only the `dev` deploy job may name `vps`. A runner cannot filter by branch itself — the guard is discipline in the workflow files. Adding a new self-hosted job means giving it one of those labels (or a new one); never name only the automatic labels.
- Killing the npm wrapper process does **not** stop the Next server: `next start` runs as a separate child (`next-server`), and `kill <npm-pid>` (or even SIGTERM without `KillMode=mixed`) leaves the child holding port 40873 — the next start then loops on `EADDRINUSE`. Always manage the dev instance through systemd (`systemctl --user restart catchlogx.service`), never by killing raw PIDs. Since #135 the dev instance runs the standalone release directly (`node ~/current/server.js`, one process, no npm wrapper), but the warning still applies to anything started via `npm start`/`next start` (local dev, older setups).
- Two user units must never manage the same app/port. `clx-app.service` (the original 2026-10-17 dev-instance unit) raced with the new `catchlogx.service` for port 40873 and caused an `EADDRINUSE` restart loop; `clx-app.service` is now stopped + disabled. If a unit "respawns" an app you just killed, check `systemctl --user list-units | grep -i clx` first. (The oneshot `catchlogx-update.service` and `~/.config/catchlogx/deploy.sh` were retired in #135 — restarts no longer build.)
- Collaborator permissions cannot be set to read-only via the API on a **user-owned** repo. `PUT /repos/{owner}/{repo}/collaborators/{user}` accepts the `permission` parameter only for organization-owned repositories: anything other than `push` (i.e. `pull`/`read`/`triage`/`maintain`) fails with `422 Cannot assign {user} permission of {role}`. Such repos therefore always invite new collaborators with write access; read-only roles have to be assigned afterwards in the web UI (Settings → Collaborators and teams → Read). Hit while setting up `CatchLogX-Data` (#125).
- `output: "standalone"` (`next.config.ts`, #135) makes `next build` copy the **whole source tree** into `.next/standalone/` — including `*.test.ts`, `docs/`, and stray files like `Fischnamen.xlsx`. Two consequences: (a) anything that scans the repo for files must exclude `.next` — Vitest did **not** and ran 6 duplicated failing test files until `exclude: [..., ".next/**"]` was added to `vitest.config.ts`; (b) published release dirs carry that noise (`docs/` inside a release is expected).
- A **self-hosted runner on a public repo** (this repo is public) means any job a fork can trigger would execute on our hardware. Mitigation in place (#135): the `deploy` job is guarded `if: github.ref == 'refs/heads/dev' && (push || workflow_dispatch)`, so fork PRs never reach the VPS runner. Keep that guard on any new self-hosted job; keep PR jobs on GitHub-hosted runners.
- `workflow_dispatch` requires the workflow file to exist on the **default branch** — here `master`, *not* the trunk `dev`. A dispatch-only workflow committed to `dev` is invisible to `gh workflow list`, `gh api repos/{owner}/{repo}/actions/workflows/<file>.yml` returns 404, and `gh workflow run --ref dev` cannot work around it. Consequence: any workflow that must be triggered **by hand** against production is unusable until a `dev` → `master` merge has happened (#138).
- `master` requires one approving review, but `enforce_admins` is **false**: the repo owner's admin token can fast-forward `master` directly (`git push origin origin/dev:master`) without a second human. That is how #141 and #142 reached `master`. Protection still binds everyone else, and the PR path is the intended one — the fast-forward is only acceptable because `dev` has already passed the full CI gate (`test` + `migration-drift`) and the deploy step there. **Check `enforce_admins` before assuming a merge needs an approval** (`gh api repos/{owner}/{repo}/branches/master/protection`); anything that must be *effective* on `master` — e.g. taking the push trigger off `production-deploy.yml` (#137) — is only pending if that flag is `true`.
- Deleting a workflow file leaves its registration in the repo: `runner-probe.yml` (file removed in #136, still listed as active) and `manual.yml` (disabled) both still appear in `gh workflow list` and the Actions UI. Such registrations are inert once the file is gone — no trigger can fire — but they clutter the manual-dispatch list; disable them via the API rather than ignoring them.
- Only **four** jobs may write to production, all in `production-maintenance.yml`, all dispatch-only on the `boku` runner, ref-guarded to `master` and armed by the typed token `confirm=ADOPT-PRODUCTION`: `cutover` (#141), `smoke-user` (#150), `release-topology` (#143) and `readonly-role` (#152). Treat that as an invariant, not a count to extend — a new production-writing path needs the same three gates and a conscious decision. Related trap: the smoke-test account's password exists **only** in the `PROD_SMOKE_PASSWORD` repository secret; do not copy it into docs, issues, checklists or a password manager, because a second copy is a second thing to leak and nothing needs it. And never point `PROD_SMOKE_USER` at a real user's name: the `smoke-user` job upserts `ADMIN` and resets the password, which is why it refuses (hard) to touch an existing account with a foreign e-mail — if it ever refuses, the secret is wrong, not the guard. The `readonly-role` password is the opposite case: it is generated **on the machine**, lives only in `/opt/CatchLogX/.env` (`READONLY_DB_PASSWORD`) and must reach the research group out of band or via the in-app page (#153) — never a repo secret, never in docs.
- The **`db push`-era app container must never be restarted against the adopted, migration-tracked production database**. Its start command runs `prisma db push`, which would re-create the pre-adoption shape (`DummyFiles` with a MinIO `filePath`, `Uploads.link`) on top of the adopted tables → data loss / schema corruption, and the adopted schema no longer matches what that old code expects. Two guards enforce this: the cutover job (#141) retires the container (`docker update --restart=no` → `docker stop` → `docker rm`) **before** it adopts, so from that moment nothing on the machine can run `db push` again, and it never brings the legacy code back (the on-machine `/opt/CatchLogX` checkout is reset to the upgrading commit and the compose file is re-checked to contain no `db push`); and the interim deploy (#142) refuses to run unless `_prisma_migrations` exists, records `20261017190000_init` as finished and leaves no half-applied migration — the **adopted-schema guard** — so the new compose can never come up against the *legacy* schema either. On a failed cutover the app stays stopped on purpose and the printed recovery contract repeats the rule; rollback means restoring the pre-cutover dump (`pg_restore --clean --if-exists`, #141), never re-running the old container against the adopted schema.
- **The production app is a systemd user unit since #143, not a container** (`catchlogx.service` → `node ~/current/server.js`). Two consequences: (a) **never `docker compose up` the app on the machine** — `docker-compose.yml` still defines the `app` service for local development, but `docker-compose.prod.yml` puts it behind the never-activated profile `interim-container`, so `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` starts **only** the database and the app container can only be started by explicitly enabling that profile (which nothing does). If both a container and the unit ever hold port 3001, the second one crash-loops on `EADDRINUSE` — the same class of fault as the dev-instance `clx-app.service`/`catchlogx.service` race (see above); the deploy job's "Retire the interim app container" step is idempotent and prevents it. (b) **the build and the runtime must be the same libc**: build with native glibc Node (`actions/setup-node` 22), never a `node:*-alpine` container — the standalone bundle's traced `bcrypt`/Prisma native binaries are musl-built there and will not load under the host's glibc Node. The workflow deliberately no longer builds in a container.
- **The immutable release must exist before the unit starts**: `publish-release.sh` repoints `~/current` and the unit's `WorkingDirectory=%h/current` needs a real `server.js`. The deploy order is publish → retire the old container → `systemctl --user restart`; an enabled-but-unstarted unit (no release yet) is the correct intermediate state, so `release-topology` (#143) only `enable`s it. Conversely the runtime env file (`/opt/CatchLogX/.env`, mode 600, gitignored) must exist **before** the build: `next build` inlines `NEXT_PUBLIC_*`, so the deploy job copies the machine's env file into the workspace first. That file is the on-machine source of truth since #143 — it survives `git reset --hard` (it is gitignored) and must never be committed or copied into the repo.
- Nothing on the production machine may run the app **twice**: the retired `clx-web` container and the systemd unit both want `127.0.0.1:3001`. `production-deploy.yml` retires the container before starting the unit and the health check is fail-fast, but if a manual `docker run`/compose ever brings the container back, the unit (or the container) will loop on `EADDRINUSE` — check `systemctl --user status catchlogx.service` and `docker ps` before "fixing" it.
- The BOKU runner is a **system** service (`actions.runner.AlphaVIE-CatchLogX.catchlogx-server.service`, launched from `/opt/actions-runner/runsvc.sh`), **not** a user service, so its jobs run with **no logind session**: `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS` and the `systemd --user` manager do not exist and `systemctl --user` fails outright (observed on the first `release-topology` dispatch, 2026-10-18). Two consequences for anything managing a *user* unit through that runner (#143): (a) the job must export `XDG_RUNTIME_DIR=/run/user/$(id -u)` and `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/$(id -u)/bus` before any `systemctl --user` (the `release-topology` and `production-deploy` jobs do this in a "Point at the user systemd manager" step); (b) **linger must already be enabled** (`sudo loginctl enable-linger clxadmin`) — `clxadmin` is in the `sudo` group but sudo still requires a password, so the runner **cannot** enable linger itself: it is a one-time on-site step, and the job fails with the exact command until it is done. `systemctl --user is-system-running` exits **non-zero** when the manager is merely `degraded`, so treat `running|degraded` as healthy, never test `if systemctl --user is-system-running` alone.
- **Postgres' `pg_hba.conf` trusts loopback**: the official image initialises it with `local all all trust` and `host all all 127.0.0.1/32 trust`, plus a catch-all `host all all all scram-sha-256` that only applies to **non-loopback** sources. So `docker exec … psql -h 127.0.0.1` (and any check inside the container) **never tests a password** — a "login works" result there proves nothing. Anything verifying credentials must connect from *outside* the container (a separate container on the same network, using the container's IP), which is what the `readonly-role` job does. Related: the database has published `0.0.0.0:5432` for a long time, so "reachable on the network" is the status quo; the boundary is the **role** (`clx_readonly`, #152: SELECT on `public` **minus** `"User"`/`"Session"`/`"PasswordResets"`, `NOSUPERUSER`/`NOCREATEDB`/`NOCREATEROLE`, `CONNECTION LIMIT 20`), not the port. And `clxadmin` still carries the **dev-default password** on that same open port — rotating it is required and must happen **after** the #143 unit cutover (the running `clx-web` container has the password baked into its compose environment), via `ALTER ROLE` + `DATABASE_URL` in `/opt/CatchLogX/.env` + `systemctl --user restart`.
