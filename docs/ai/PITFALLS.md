# Pitfalls

Things that do not work, subtle bugs, and non-obvious constraints.
Read this file carefully before making changes in affected areas.

- Prisma client is at `app/generated/prisma/` — import as `"../app/generated/prisma"`, NOT `@prisma/client`. The generated directory is gitignored and fully untracked, so nothing in git history or CI regenerates it.
- After ANY schema change, run `npm run prisma:generate` (#151) — Next.js does not auto-regenerate the Prisma client. `npm install` now also regenerates it via the `postinstall` script, but a bare `git pull` does not: pulling a schema refactor leaves the client stale until a regenerate or install. Symptom when stale: dozens of `Property 'X' does not exist on type 'PrismaClient'` / unknown-relation typecheck errors (37 errors after pulling the #131 blob refactor), which the pre-push hook turns into an aborted push even though the code itself is fine and CI is green. Fix is always `npm run prisma:generate`, never a code change.
- Schema changes go through the migration history: `npx prisma migrate dev --name <name>` locally, `npx prisma migrate deploy` on the dev instance/production. **Never `prisma db push`** — it bypasses the history and drops/recreates tables on renames (that is how the history drifted before #129). Needs `SHADOW_DATABASE_URL` (`clx_shadow`) for local `migrate dev`
- `middleware.ts` runs in Edge Runtime — Prisma cannot be imported there. Keep it to lightweight cookie checks only
- Uploads are limited to **20 files / 500 MiB total / 32 MiB per file** (`MAX_UPLOAD_FILES`/`MAX_UPLOAD_TOTAL_BYTES`/`MAX_UPLOAD_FILE_BYTES` in `lib/uploadReport.ts`). There is **no row limit**: a "10,000 rows per file" rule lived only as UI text until it was briefly enforced, and it blocked the real BOKU bulk (14 files, 247,240 rows, 38 MB — `CatchLogX-Data`). **Two reverse-proxy settings must both be raised, or large uploads fail before the app sees them** (#132): `client_max_body_size` (nginx default 1m → **413**) *and* `proxy_read_timeout`/`proxy_send_timeout` (default 60s → **504** on a slow workbook). Both reach the browser as a generic error; `uploadFiles` now reports the HTTP status instead (`describeHttpFailure` in `lib/upload-client.ts`). Dev instance vhost: `client_max_body_size 550m`, timeouts `600s`.
- Bulk-upload memory/CPU is the real constraint for big workbooks, not the proxy: the route buffers the **whole body in memory** (`req.formData()`) and validation parses each workbook with SheetJS. Two measures keep it workable (#132): `XLSX.read(..., { dense: true })` (rows as arrays — measured ~2x faster and ~35% lower parse peak than the default sparse mode) and releasing each file's rows right after validation in `processBulkUpload` (re-read via `readDataRowsForAnnotation` only to annotate a failed workbook). Measured on the real 247k-row bulk: **~33 s** success path, **~77 s** when an error report is built, peak **~1.5 GB RSS** on this 3.8 GB VPS — i.e. close to the available memory. A 504'd request **keeps running server-side** and can still commit, so check `journalctl --user -u catchlogx.service` if a user reports a failure after a long upload.
- PostgreSQL must be running for any app to work (`docker compose up -d db`). File uploads and downloads need no extra service — bytes live in the DB (`FileBlob`, #131)
- `lib/mailer.ts` throws if nodemailer env vars are missing — password reset routes will fail without configured SMTP
- `scripts/create-user.ts` hardcodes `admin`/`admin` credentials — dev-only script, NOT for production
- Docker Compose `app` service runs `npx prisma migrate deploy` on every startup — it applies pending migrations only, never schema drift silently. The `db-shadow-init` service creates `clx_shadow` for `migrate dev` (#129)
- `no-explicit-any` ESLint rule is disabled — TypeScript `any` is allowed in this codebase
- `overrides` in `package.json` pins `@types/node` to the root spec (`"$@types/node"`): vitest 5 requires peerOptional `@types/node ^22 || >=24`, which breaks `npm ci` with ERESOLVE on clean machines while a stale local `node_modules` masks it. After touching any `@types/*` range, always verify with a fresh `rm -rf node_modules && npm install`.
- `next-env.d.ts` is gitignored and only auto-generated by `next dev`/`next build`. It carries `/// <reference types="next/image-types/global" />`, which is what makes `import x from "@/assets/img/foo.png"` typecheck. CI/the pre-push hook never run `next dev`/`next build`, so `npm run typecheck` (`tsc --noEmit`) fails there with `Cannot find module '...png'` even though it passes locally (where `next-env.d.ts` already exists from a prior dev run) — masked the same way the `@types/node` issue above was. Fixed by tracking `types/next-image.d.ts` with just that one reference line, independent of the gitignored file. To repro/verify locally: temporarily `mv next-env.d.ts next-env.d.ts.bak` before running `npm run typecheck`.
- `validateSQLQuery` (`services/queryService.ts`) is a keyword blocklist (whole-word match since #116), not a security boundary — it can't see through e.g. Postgres unicode-escaped identifiers. Real protection for the query UI would be a read-only DB role.
- Unit tests mock Prisma call shapes (`vi.mock("@/lib/prisma")`). Changing a query's `where`/`data`/`select` can fail tests that assert on those arguments even when behaviour is unchanged — adjust the assertion, don't delete the test.
- Self-hosted runners are selected by **label, not by branch**. Every self-hosted runner automatically carries `self-hosted`, `Linux` and `X64`, so two runners with only those automatic labels are *both* eligible for every `runs-on: [self-hosted, …]` job and placement becomes nondeterministic. The repo is a personal **user** account (`georgernstgraf`), so runner *groups* are not available as a scoping mechanism — custom labels are the only lever. Give each runner a distinct custom label (e.g. `boku-prod`, `vps-dev`) and never rely on the automatic ones alone. This matters concretely: `production-deploy.yml` builds, publishes and restarts the unit **on that machine**, and reads `/home/clxadmin/.config/catchlogx/.env` — none of that exists anywhere else. Since #136 each machine-specific job names its own custom label (`vps` → this VPS, `boku` → the BOKU machine), so placement is deterministic: `dev` builds on `vps`, `master` on `boku`. **Invariant**: only `master`-triggered workflows may name `boku` (the BOKU machine must never be pulled into `dev` work), and only the `dev` deploy job may name `vps`. A runner cannot filter by branch itself — the guard is discipline in the workflow files. Adding a new self-hosted job means giving it one of those labels (or a new one); never name only the automatic labels.
- Killing the npm wrapper process does **not** stop the Next server: `next start` runs as a separate child (`next-server`), and `kill <npm-pid>` (or even SIGTERM without `KillMode=mixed`) leaves the child holding port 40873 — the next start then loops on `EADDRINUSE`. Always manage the dev instance through systemd (`systemctl --user restart catchlogx.service`), never by killing raw PIDs. Since #135 the dev instance runs the standalone release directly (`node ~/current/server.js`, one process, no npm wrapper), but the warning still applies to anything started via `npm start`/`next start` (local dev, older setups).
- Two user units must never manage the same app/port. `clx-app.service` (the original 2026-10-17 dev-instance unit) raced with the new `catchlogx.service` for port 40873 and caused an `EADDRINUSE` restart loop; `clx-app.service` is now stopped + disabled. If a unit "respawns" an app you just killed, check `systemctl --user list-units | grep -i clx` first. (The oneshot `catchlogx-update.service` and `~/.config/catchlogx/deploy.sh` were retired in #135 — restarts no longer build.)
- Collaborator permissions cannot be set to read-only via the API on a **user-owned** repo. `PUT /repos/{owner}/{repo}/collaborators/{user}` accepts the `permission` parameter only for organization-owned repositories: anything other than `push` (i.e. `pull`/`read`/`triage`/`maintain`) fails with `422 Cannot assign {user} permission of {role}`. Such repos therefore always invite new collaborators with write access. **Correction (2026-10-18):** the web UI does **not** offer the workaround either — on a *private* user-owned repo the *Settings → Collaborators and teams* list has no role menu (only the remove button); collaborator roles are only available for organization-owned repos (or with a Team/Enterprise plan). See [community discussion #77312](https://github.com/orgs/community/discussions/77312). Hit while setting up `CatchLogX-Data` (#125); resolved by accepting write access deliberately (`CatchLogX-Data#2`, decision D007 in the data repo).
- `output: "standalone"` (`next.config.ts`, #135) makes `next build` copy the **whole source tree** into `.next/standalone/` — including `*.test.ts`, `docs/`, and stray files like `Fischnamen.xlsx`. Two consequences: (a) anything that scans the repo for files must exclude `.next` — Vitest did **not** and ran 6 duplicated failing test files until `exclude: [..., ".next/**"]` was added to `vitest.config.ts`; (b) published release dirs carry that noise (`docs/` inside a release is expected).
- A **self-hosted runner on a public repo** (this repo is public) means any job a fork can trigger would execute on our hardware. Mitigation in place (#135): the `deploy` job is guarded `if: github.ref == 'refs/heads/dev' && (push || workflow_dispatch)`, so fork PRs never reach the VPS runner. Keep that guard on any new self-hosted job; keep PR jobs on GitHub-hosted runners.
- `workflow_dispatch` requires the workflow file to exist on the **default branch** — here `master`, *not* the trunk `dev`. A dispatch-only workflow committed to `dev` is invisible to `gh workflow list`, `gh api repos/{owner}/{repo}/actions/workflows/<file>.yml` returns 404, and `gh workflow run --ref dev` cannot work around it. Consequence: any workflow that must be triggered **by hand** against production is unusable until a `dev` → `master` merge has happened (#138).
- `master` requires one approving review, but `enforce_admins` is **false**: the repo owner's admin token can fast-forward `master` directly (`git push origin origin/dev:master`) without a second human. That is how #141 and #142 reached `master`. Protection still binds everyone else, and the PR path is the intended one — the fast-forward is only acceptable because `dev` has already passed the full CI gate (`test` + `migration-drift`) and the deploy step there. **Check `enforce_admins` before assuming a merge needs an approval** (`gh api repos/{owner}/{repo}/branches/master/protection`); anything that must be *effective* on `master` — e.g. taking the push trigger off `production-deploy.yml` (#137) — is only pending if that flag is `true`.
- Deleting a workflow file leaves its registration in the repo: `runner-probe.yml` (file removed in #136, still listed as active) and `manual.yml` (disabled) both still appear in `gh workflow list` and the Actions UI. Such registrations are inert once the file is gone — no trigger can fire — but they clutter the manual-dispatch list; disable them via the API rather than ignoring them.
- **Production maintenance runs over SSH, not through a workflow** (#170). `production-maintenance.yml` is deleted: its five one-shot jobs had run (audit #138, rehearsal #140, cutover #141, smoke user #150, release topology #143) and the three recurring ones now live as versioned scripts run from a root-owned checkout of this repo (`git clone https://github.com/georgernstgraf/CatchLogX /root/CatchLogX`; re-clone when stale — the old `/opt/CatchLogX` checkout is deleted with #122) (`deploy/prod/postgres/*.sh`, `deploy/prod/postgres/observability-extension.sql`, `deploy/postgres/report.sql`; runbook `deploy/prod/postgres/README.md`). Access is `root` over the BOKU VPN — the sanctioned path per `DECISIONS.md` (2026-10-16) — so there is no longer a CI gate in front of production writes; the gate is the human with VPN + key, and the runbook is reviewed in git. The self-hosted `boku` runner still exists and still deploys `master` via `production-deploy.yml`. The `readonly-role` password stays what it always was: generated **on the machine**, only in `/home/clxadmin/.config/catchlogx/.env` (`READONLY_DB_PASSWORD`), never a repo secret, never in docs — rotation is `readonly-role.sh` without `KEEP_PASSWORD=1`.
- **The base `docker-compose.yml` must never run on the production machine**. It still defines the students' local stack: `db` would publish `0.0.0.0:5432` (clash with the native cluster) and `app` would run its start command — migrate, **seed fish species** (`scripts/insert-fish.ts`), build, bind `:3001` (clash with the unit). `docker-compose.prod.yml` therefore puts **every** service behind a never-activated profile (`retired-db`, `interim-container`), so `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` starts nothing. `docker compose config --services` with the override must print an empty list — if it ever prints a service, the guard is broken. (Historical: the `db push`-era app container `clx-web` was retired in the cutover #141; the compose-profile guard replaced that removal step as the structural protection.)
- **The production app is a systemd user unit since #143, not a container** (`catchlogx.service` → `node ~/current/server.js`). Two consequences: (a) **never `docker compose up` the app on the machine** — `docker-compose.yml` still defines the `app` service for local development, but `docker-compose.prod.yml` puts it behind the never-activated profile `interim-container`, so `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d` starts **only** the database and the app container can only be started by explicitly enabling that profile (which nothing does). If both a container and the unit ever hold port 3001, the second one crash-loops on `EADDRINUSE` — the same class of fault as the dev-instance `clx-app.service`/`catchlogx.service` race (see above); the deploy job's "Retire the interim app container" step is idempotent and prevents it. (b) **the build and the runtime must be the same libc**: build with native glibc Node (`actions/setup-node` 22), never a `node:*-alpine` container — the standalone bundle's traced `bcrypt`/Prisma native binaries are musl-built there and will not load under the host's glibc Node. The workflow deliberately no longer builds in a container.
- **The immutable release must exist before the unit starts**: `publish-release.sh` repoints `~/current` and the unit's `WorkingDirectory=%h/current` needs a real `server.js`. The deploy order is publish → `systemctl --user restart`; an enabled-but-unstarted unit (no release yet) is the correct intermediate state, so `release-topology` (#143) only `enable`s it. Conversely the runtime env file (`/home/clxadmin/.config/catchlogx/.env`, mode 600, outside the repo) must exist **before** the build: `next build` inlines `NEXT_PUBLIC_*`, so the deploy job copies the machine's env file into the workspace first. That file is the on-machine source of truth since #143 — and since #122 it lives in `clxadmin`'s home, so a `git reset --hard` in any checkout cannot touch it — and it must never be committed or copied into the repo.
- Nothing on the production machine may run the app **twice**: the retired `clx-web` container and the systemd unit both want `127.0.0.1:3001`. The docker-based removal step is gone with #122 (`clxadmin` has no docker group any more); the container was retired in #143, so the unit owns the port. If a manual `docker run`/compose ever brings a container back, the unit (or the container) will loop on `EADDRINUSE` — check `systemctl --user status catchlogx.service` and `docker ps` before "fixing" it.
- The BOKU runner is a **user** unit of `clxadmin` since 2026-10-29 (#122): `~/.config/systemd/user/actions.runner.AlphaVIE-CatchLogX.catchlogx-server.service`, working directory `~/actions-runner`, `Restart=always`, `WantedBy=default.target`, kept alive at boot by linger (`Linger=yes` for `clxadmin`; a rebuilt host needs `loginctl enable-linger clxadmin` **as root**, because the account has no sudo). Before that it was a *system* service whose jobs had **no logind session** — the deploy job still exports `XDG_RUNTIME_DIR=/run/user/$(id -u)` and `DBUS_SESSION_BUS_ADDRESS` in its "Point at the user systemd manager" step, which is defensive and harmless. `systemctl --user is-system-running` exits **non-zero** when the manager is merely `degraded`, so treat `running|degraded` as healthy, never test `if systemctl --user is-system-running` alone. Two traps found while moving it: (a) `~/actions-runner/bin` and `~/actions-runner/externals` were **absolute** symlinks into `/opt/actions-runner`, so the service died with **status 127** right after the move — they are relative now (`bin -> bin.2.338.0`, `externals -> externals.2.338.0`), which also survives a runner self-update; (b) reading user-unit logs as root is not `journalctl -M clxadmin@` (that fails with "Connecting to a machine as non-root is not supported") — use `runuser -u clxadmin -- env XDG_RUNTIME_DIR=/run/user/1000 journalctl --user-unit <unit>`.
- **`clxadmin` is an unprivileged app account since 2026-10-29 (#122)**: no `sudo`, `docker` or `lxd` group — `sudo -l -U clxadmin` must answer "not allowed" and `id clxadmin` must not list them. Everything the app, the runner and the backup timer do is unprivileged (systemd user manager, `peer` auth to Postgres, outbound HTTPS). Anything needing root happens as **`root` over the BOKU VPN**, or as `runuser -u clxadmin -- …` from that root session (peer auth, restores, `readonly-role.sh`). **Deliberate exception: `root` keeps password login on the console** (`getty@tty1` → `/bin/login` → PAM; `PermitRootLogin prohibit-password` restricts only sshd). Do not "harden" that away — `passwd -l root`, `PermitRootLogin no`, `AllowUsers`/`DenyUsers` for root and `pam_securetty` are off limits, that is the break-glass path. SSH itself is keys-only for everyone (`PasswordAuthentication no`): `clxadmin`'s password is locked (`passwd -l`) and its **key** login still works, because `pam_unix` in the *account* phase only checks expiry, not the lock.
- **A loopback connection never tests the password** — that was true inside the old container (`local all all trust`, `host all all 127.0.0.1/32 trust`, catch-all `scram` only for non-loopback sources) and is still true on the native cluster: the socket uses `peer` for `postgres` and `clxadmin`, and `127.0.0.1` uses `scram` only because the app connects there. Anything that verifies credentials must connect from a **non-loopback source** — on production `psql "host=141.244.222.191 … sslmode=require"` (`readonly-role.sh` does exactly that). The boundary is the **role** (`clx_readonly`, #152: SELECT on `public` **minus** `"User"`/`"Session"`/`"PasswordResets"`, `NOSUPERUSER`/`NOCREATEDB`/`NOCREATEROLE`, `CONNECTION LIMIT 40`), not the port. `clxadmin` carried the dev-default password on that open port until 2026-10-27 and was rotated in the on-site window (`ALTER ROLE … PASSWORD`, `DATABASE_URL` rewritten, `systemctl --user restart`); verify such a rotation **from outside** the host, never on the socket. Note `psql -c "… :'pw'"` does **not** interpolate variables — pipe the statement through stdin with `-v pw=…` (or `\getenv`).
- **Dev-DB is native PostgreSQL since #168 (2026-10-28) — with a stopped fallback container**: `postgresql@16-main` (PGDG 16.15) listens on `0.0.0.0:5432`, `clxadmin`'s password lives in `~/dev-stack/.env` (`CLXADMIN_PASSWORD`) **and** in the app's repo `.env` (`DATABASE_URL`/`SHADOW_DATABASE_URL` — both were updated during the migration; the app unit reads that file, so a future rotation means three places, not two). The old rootless container `clx-postgres` is **stopped, not removed** (`clx_pgdata` volume intact): restarting it while the native cluster holds 5432 fails with a port clash — do **not** "clean up" the container without decommissioning this pitfall deliberately. TLS is mandatory for everything non-loopback (`hostssl` + `host … reject` in `/etc/postgresql/16/main/pg_hba.conf`); certbot renewals propagate via `/etc/letsencrypt/renewal-hooks/deploy/catchlogx-pg-tls-sync.sh` into `/var/lib/postgresql/tls/` (postgres-owned, key 0600 — Postgres refuses to start with a group/world-readable key). The PITFALLS-#36 rule above is now trivially satisfiable on dev (real client IPs reach Postgres), but still applies to the BOKU production container.
- **Several Prisma models are `@@map`'d, so the physical table names are not the model names**: `FishCatch` → `fish_catches`, `Sampling` → `samplings`, `RiverSite` → `river_sites`, `FishSpecies` → `fish_species`, while `User`, `Session`, `Uploads`, `TemplateFiles`, `FileBlob`, `UserQueries`, `PasswordResets` are unmapped. Raw SQL against production (the `readonly-role` verification, the SQL query UI, the R statistics) must use the physical names — `SELECT … FROM "FishCatch"` fails with `relation "FishCatch" does not exist`. The `readonly-role` job therefore resolves table names from `pg_tables` instead of hardcoding them, and it resolves the auth tables (drift guard) before granting anything.
- **The production host has no DHCP any more, by design** (#122, 2026-10-27). Subiquity had installed it with `dhcp4: true`; a reboot handed the box a different lease address and locked every user out, because staff and `NEXT_PUBLIC_APP_URL` point at a fixed address. `/etc/netplan/00-installer-config.yaml` is now static (`141.244.222.191/21` since #164 — the first run pinned `.9` by mistake, gateway `141.244.216.1`, DNS `141.244.7.11`/`.10`), with **no** DHCP on either NIC, and the time service pinned to the BOKU servers in `/etc/chrony/sources.d/10-boku.sources`. Two constraints: netplan 1.2 has **no** `use-address` key (`netplan generate` fails with `unknown key`), so "static address + everything else from DHCP" is not expressible — the values are pinned instead; and the address must be excluded from the DHCP pool by BOKU-IT, otherwise another host can be handed it and cause a conflict. A broken `/etc/netplan/*.yaml` is worse than an unreachable box: if `netplan generate` fails, the next boot comes up **without any address**, so always validate with `netplan generate` and arm an auto-rollback (`systemd-run --on-active=180 … netplan apply`) before touching a live address. Changing the address also means changing it in **three** places that are not coupled: netplan, `/home/clxadmin/.config/catchlogx/.env` (`NEXT_PUBLIC_APP_URL`/`NEXTAUTH_URL`), and `deploy/prod/nginx/sites-available/catchlogx` (the `listen <ip>:3001` redirect).
- **`systemd-networkd-wait-online` can cost 2 minutes of every boot**: netplan generates a wait-online drop-in that names *every* interface it manages, so a second NIC without carrier (`enp3s0` here) blocks the whole userspace startup until the 120 s cap (measured 2 min 05 s). `optional: true` in netplan is **not** enough (in netplan 1.2 it did not emit `RequiredForOnline=no`). Fix: `/etc/systemd/system/systemd-networkd-wait-online.service.d/99-any-link.conf` with an `ExecStart=` (resets the list) followed by `ExecStart=/usr/lib/systemd/systemd-networkd-wait-online -i eno1 --timeout=15`. Do **not** use a bare `--any`: `docker0`/the bridges carry routable addresses and would count as "online", so the unit would pass before the real NIC is up. Result: 23.8 s boot, ~7 s userspace.
- **`actions/checkout` cannot resolve a short SHA** (#163): `ref: 38aad29` fails with `A branch or tag with the name '38aad29' could not be found` — it resolves branches and tags only. Production stayed untouched, but the rollback drill failed for the wrong reason. Every rollback instruction must name the **full** SHA (`git rev-parse <short>`); that is what `ARCHITECTURE.md` and the job summaries must say.
- **`sha256sum -c` verifies against the filename listed in the checksum file** (fix `2546d44`): `release-topology` downloaded `node-v22.23.3-linux-x64.tar.xz` as `node.tar.xz`, so the check failed with `FAILED open or read` on its first real run. Download artefacts under their upstream name before verifying, and extract the same file.
- **`apt-get upgrade` silently holds the docker stack back** (#122): `docker-ce`/`containerd.io` need dependencies that plain `upgrade` will not add, so it upgrades `docker-ce-cli` and leaves the daemon old. Use `apt-get full-upgrade` inside a maintenance window — it replaces `dockerd` and `containerd`, so every container restarts (the app blips ~10–20 s, then `unless-stopped` brings it back). Run it as a transient unit (`systemd-run --unit=… --property=Type=oneshot …`) so an SSH drop cannot interrupt dpkg mid-transaction, with `DEBIAN_FRONTEND=noninteractive` and `-o Dpkg::Options::=--force-confold`. Afterwards `unattended-upgrades` covers `resolute-updates` daily, with `docker`/`containerd` blacklisted and no automatic reboot.
- **The deploy used to leave the runtime env inside every release** (#162, fixed with #164): `production-deploy.yml` copies `/home/clxadmin/.config/catchlogx/.env` into the workspace because `next build` inlines `NEXT_PUBLIC_*`, and Next's standalone output **also copies the workspace `.env` into `.next/standalone/`** — so the secrets (and, after a rotation, the *old* password) ended up in `~/releases/<sha>/.env`, not just in the workspace. `rm -f .env` after the build alone is therefore not enough: the deploy now removes `.env` **and** `.next/standalone/.env`, and `publish-release.sh` drops `$REL/.env` as a second line of defence. The unit only ever reads `EnvironmentFile=/home/clxadmin/.config/catchlogx/.env`.
- **There is no host firewall on the production machine**: `ufw` is inactive and the only nftables rules are docker's own (dnat + forward), and `5432` is unfiltered — so the access boundary is the database **role** (#152), not the network. Do not assume `ufw` protects anything when reasoning about this host. Since #164 the *app* is not network-reachable at all (`127.0.0.1:3001` behind nginx), but nginx is (ports 80 and the `:3001` redirect), so "the app is on loopback" is not the same as "the host exposes nothing".
- **The production app only binds loopback since #164, and nginx owns the public ports** — three non-obvious couplings: (a) the redirect on `141.244.222.191:3001` and the app on `127.0.0.1:3001` can share port 3001 **because the addresses differ**; `0.0.0.0:3001` + `127.0.0.1:3001` is `EADDRINUSE` (verified), so never "simplify" the redirect to a wildcard listener without moving the app. (b) `HOSTNAME=127.0.0.1` is set in the unit **and** in the `release-topology` job template — changing only one means the next re-provision silently re-exposes the app on `0.0.0.0`. (c) nginx binds a fixed IP, so it must start after the address exists: `nginx.service.d/99-catchlogx-address.conf` orders it `After=network-online.target` and sets `Restart=on-failure`; without it nginx dies at boot on "cannot assign requested address" and the site is down even though the app is up. Machine-side config is mirrored (secrets-free) in `deploy/prod/`.
- **`NEXT_PUBLIC_*` is inlined at build time, so an address change is not an `.env` change**: after correcting `NEXT_PUBLIC_APP_URL`, the *running* release still carries the old host in `~/current/.next/server/chunks/*` (only `passwordService` uses it, for the reset link). Changing `/home/clxadmin/.config/catchlogx/.env` + restart fixes `NEXTAUTH_URL` but **not** the inlined value — that needs a deploy dispatch (rebuild). Verify with `grep -r '<new-host>' ~/current/.next`.
- **Agents run on every machine that clones this repo — there is no sandbox.** An agent session's shell can be live infrastructure: on the dev VPS (`claw.graf.priv.at`, served as `catchlogx.graf.priv.at`, user `catchlogx`) it shares the host with `catchlogx.service` (app, port 40873) and the `vps` deploy runner; on the BOKU machine lives the `boku` runner. Identify the host at session start (`hostname`, `whoami`, `systemctl --user list-units | grep -i clx`) before stopping/restarting/killing anything — user units and listening ports are live services, not a playground (see the EADDRINUSE and raw-PID pitfalls above, and the ~3.8 GB RAM ceiling on this VPS that bulk uploads already push).

- **`ALTER SYSTEM SET shared_preload_libraries = 'a,b'` stores the list as ONE library name and the server refuses to start** (hit on the dev cluster on 2026-10-29: `FATAL: could not access file "auto_explain,pg_stat_statements"`, database down until `postgresql.auto.conf` was fixed by hand). For a GUC list the value must be a **bare** comma-separated list (`= auto_explain, pg_stat_statements`); quoting it as a single string (also via psql `:'var'`) makes `ALTER SYSTEM` write `'"a,b"'`. `deploy/postgres/observability.sql` therefore builds the statement with `format(...)` + `\gexec`, and the production job backs up `postgresql.auto.conf` before the restart and restores it if the server does not come up. A `DO` block cannot help here: `ALTER SYSTEM cannot be executed from a function`.
- **Extension GUCs do not exist before the library is preloaded**: `ALTER SYSTEM SET pg_stat_statements.max` / `auto_explain.log_min_duration` fails with `unrecognized configuration parameter` on a server that has not restarted with the library. That is why `observability.sql` is a **two-pass** script: pass 1 writes `shared_preload_libraries` + the core/log settings, then a restart, then pass 2 sets the extension GUCs and creates the extension. Do not "fix" it into one pass.
- **`pg_stat_statements` grants `SELECT` to `PUBLIC`** when the extension is created (`pg_stat_statements--1.10.sql`); the view shows the query text of **all** roles. Without `REVOKE SELECT ON pg_stat_statements FROM PUBLIC` the published `clx_readonly` password could read the auth flows and every app query. Both apply paths revoke it (`observability.sql`, and `deploy/prod/postgres/observability-extension.sql` for the native production cluster), and `readonly-role.sh` is the place to re-check when in doubt. The app role stays superuser (#166), so it keeps access either way.
- **The production database is a native cluster since 2026-10-30 (#170)** — three traps that only exist there:
  - **Port 5432 can only be held by one of them.** The native cluster and the stopped `clx-postgres` container both want it. Order in the window was: `docker update --restart=no` → `docker stop` → `systemctl start postgresql@16-main`. Never start the container "to have a look"; while the rollback path exists, `start.conf = manual` keeps the cluster from coming up at boot (so a reboot with the rollback active starts only the container). `systemctl is-enabled postgresql@16-main` may report `enabled-runtime` — that is the `postgresql-generator` at work, not a defect.
  - **The locale must stay `en_US.utf8`.** The container database used it; a fresh PGDG cluster on Ubuntu defaults to `C.UTF-8`. Creating `clx` without `--locale=en_US.UTF-8` silently changes text sort order for the research group (`provision-cluster.sh` and the runbook do it explicitly). Check with `SELECT datcollate FROM pg_database WHERE datname='clx'`.
  - **Peer auth is what makes the backup work.** The units run as `clxadmin`, and `pg_hba.conf` has `local all clxadmin peer`; `backup.sh` deliberately uses `-w` so a missing rule fails immediately instead of waiting for a password under systemd. Restores must run as `clxadmin` too (`runuser -u clxadmin --`), otherwise the tables end up owned by the wrong role. Rotations are verified **from outside** (`psql -h 141.244.222.191 … sslmode=require`), never on the socket — a socket login proves nothing about password auth.
  - **TLS is offered, not enforced** (`ssl = on`, self-signed cert, no CA in the BOKUnet). libpq's default `sslmode=prefer` encrypts automatically; `sslmode=require` enforces; `verify-full` cannot work. Do not "harden" it to `hostssl`-only without asking: that would lock out every R client that does not set sslmode (#170, `deploy/prod/postgres/`).
- **`logging_collector = on` changes where the logs are**: statement/connection lines do not appear in `journalctl`/`docker logs` — they land in `<PGDATA>/log/postgresql-<weekday>.log` (production since #170: `/var/lib/postgresql/16/main/log`, mode 0600 postgres; the stopped container's copies live inside its volume). Read them with `tail -n 200 /var/lib/postgresql/16/main/log/postgresql-$(date +%a).log` (as root). `log_directory = 'log'` is **relative to PGDATA**, so the files do not move with `log_directory` changes alone. `log_parameter_max_length = 0` keeps bind values out of the slow-query log, but `auto_explain` plans still contain literal filter values — those logs must stay on the machine, never in a public artifact.
- **`CREATE INDEX CONCURRENTLY` cannot run inside a transaction block**, and Prisma wraps each migration in one. An index on a large table (prod `fish_catches` ≈ 465k rows) therefore needs a hand-written migration with the `CONCURRENTLY` variant and the transaction wrapper disabled; otherwise the table is write-locked while the index builds. Evidence for *which* index to add comes from `deploy/postgres/report.sql` plus `EXPLAIN (ANALYZE, BUFFERS)` before/after — a `Seq Scan` on a small lookup table is the planner's correct choice, not a bug.
- **The retired dev container `clx-postgres` is stopped with `restart=no`** (2026-10-29), Volume `dev-stack_clx_pgdata` intact — it is the fallback copy of the pre-#168 database, not a service. Starting it while the native cluster holds `0.0.0.0:5432` fails with a port clash; never start it "to have a look". The native cluster itself starts at boot through the `postgresql-generator` (it creates `postgresql.service.wants/postgresql@16-main.service` from `/etc/postgresql/16/main/start.conf` = `auto`), so `systemctl is-enabled postgresql@16-main` reporting `enabled-runtime` is misleading, not a defect.
- **There is no per-IP connection limit in PostgreSQL — and a timeout is never a database limit** (#171). The only ceilings are `max_connections` (global, package default **100** when unset), `superuser_reserved_connections`, `reserved_connections` and `CONNECTION LIMIT` **per role** — nothing keyed on the client address. A real limit answers **immediately** with `FATAL: too many connections for role …` / `FATAL: sorry, too many clients already` / `no pg_hba.conf entry`; a **hang or timeout** means the packet never arrived or the handshake stalled. The classic false alarm is a stale tunnel/conntrack state (after a VPN hiccup existing flows keep working while every *new* SYN goes unanswered) — that reproduces exactly the "one connection works, every further one times out" report. Distinguish in three steps: (1) `log_connections = on` in `<PGDATA>/log/postgresql-<day>.log` — is there a `connection received` line for the failing attempt? (2) `ss -tan '( dport = :5432 )'` — several `ESTAB` from one source IP only prove the kernel backlog, not the postmaster; (3) send real **startup packets**: four parallel `PGPASSWORD=wrong psql … sslmode=require` attempts must each answer `FATAL: password authentication failed` after ~1.3 s (TLS + SCRAM + `auth_delay`). Four answers = four connections served simultaneously from one address, no password needed. If a per-address cap is ever really wanted it is an nftables conntrack rule, and it **must exempt loopback** — the app's Prisma pool opens more than 5 connections and would be locked out.
- **A clean PostgreSQL restart does not throw away `pg_stat_statements`** — `pg_stat_statements.save` defaults to `on`, so the shared-memory counters are written to `$PGDATA/pg_stat_statements.stat` at shutdown and reloaded at startup (verified 2026-10-29 during the #171 rollout: `tracked_shapes = 198` and an unchanged `stats_reset` after `systemctl restart postgresql@16-main`). Only `pg_stat_statements_reset()`/`pg_stat_reset()` or an **unclean** shutdown loses the window. Do not plan a measurement restart around a loss that will not happen — and do not rely on a restart to "start fresh" either.
- **The dev VPS `claw` is not reachable on the public SSH port** — `85.215.162.182:22` (`claw.graf.priv.at` / `catchlogx.graf.priv.at`) refuses connections while 443 and 5432 are open. The way in is the WireGuard/OpenVPN tunnel: `ssh claw` uses `Hostname 10.8.0.2`, `User georg` (`ssh clawc` is the same host as `catchlogx`), and `georg` has passwordless sudo. There is **no source checkout** on that host: the app is published by the self-hosted runner into `~/releases/<sha>` for the `catchlogx` user, so config files are copied there (`scp … claw:/tmp/`) or fetched from raw.githubusercontent.com. The database config lives in `/etc/postgresql/16/main/conf.d/` (`99-catchlogx-tls.conf`, `99-catchlogx-capacity.conf` — the latter versioned as `deploy/vps/postgres/`).
- **The prod host has three Node installations and `PATH` only reaches one of them, only in a login shell** (#172). `~/tools/node/bin/node` runs the app (`ExecStart=`), `~/actions-runner/externals/node24/bin/node` runs the runner itself, and `actions/setup-node` unpacks a third per deploy job into `_work/_tool/`. None of them is on the system `PATH`: `ssh clxadmin@host 'node -v'` fails with `command not found` (ssh starts a **non-login** shell), while `ssh clxadmin@host 'bash -lc "node -v"'` prints v22.23.3. Since 2026-10-29 that is deliberate — `~/.config/catchlogx/path.sh` (versioned as `deploy/prod/shell/node-path.sh`) is sourced from `~/.profile` only. `systemd` never reads `.profile`, so the units are unaffected by PATH changes, and a Node bump is `ln -sfn ~/tools/node-v22.<x>.<y> ~/tools/node` + restart. For `prisma migrate status` use the hand-maintained clone `~/src/CatchLogX`: it tracks **`master`** (prod runs `master`; on `dev` unreleased migrations show up as bogus "pending") and its `.env` is a symlink to `~/.config/catchlogx/.env`, so there is one DB password. A clone is only a diagnosis tool — always cross-check `readlink -f ~/current` against `git -C ~/src/CatchLogX rev-parse HEAD`, because nothing rotates the clone for you.
